Stay deep in the code. Keep a way back.

An absorbing problem can make time slip from view. Stepping away can mean rebuilding the context when you return. paperkinn brings companion-style care into the coding conversation, with context-aware reminders, agreed pause boundaries and a clear next step to return to.

Built for ADHD and neurodivergent developers. The founder-tested personal prototype has tiered care boundaries and optional stops on the companion’s task work. Experimental Model Context Protocol (MCP) plugins and external trials are in development.

01 The prototype

A companion that can hold the pause you agreed to.

The care system grew through repeated refinement in Mori, Z’s personal companion prototype. It combines the conversation with a record of current care needs, earlier reminders and completed actions. Support can move from a reminder to a firmer boundary, then a stop on further task work.

With care stops enabled, the companion asks for explicit confirmation that the break happened. “I’ll take a break” leaves it ahead of you; “I took a break” clears the matching boundary. Recognizing that return is part of care, too.

What works today: the personal prototype tracks care state, applies tiered boundaries and clears the matching boundary after confirmation. It can pause its own task work when routine stops are enabled.

What comes next: package those behaviors into MCP plugins for Claude-based agents, then test them with external developers. The personal prototype does not establish benefits for other users.

How situational context informs care boundaries

The prototype checks local time, work-episode length, available calendar context and explicit reports of completed care actions. Conversation-derived signals, such as repeated troubleshooting, are fallible clues rather than diagnoses.

A scheduled meal can anchor a pause. A recent meal report can suppress another meal prompt. An active calendar event can defer a water reminder. Time thresholds remain guardrails; context changes how they apply. Stale or missing records can still cause mistakes, which we continue to test.

  1. 01 /

    Start with a reminder.

    The companion brings the pause into the conversation while keeping the current task in view.

  2. 02 /

    Hold a firmer boundary.

    Higher tiers make the boundary explicit. With routine stops enabled, the companion can decline further task work until the requested action is confirmed complete.

  3. 03 /

    Recognize the return.

    Confirmation clears the matching boundary. The aim is a brief, useful return to the task, without a lecture or another demand for the same break.

You stay in control of the companion. You can switch routine work stops off while keeping reminders and separate safety rules. In the current prototype, that opt-out lasts until the companion service restarts. paperkinn’s MCP packaging and wider user testing are in development.
02 Why another tool?

Care belongs inside the agent runtime.

Planners, human coworking and conversational coaches each offer useful support. Claude Code already provides memory and session tools. paperkinn focuses on care within the working conversation: when to stay quiet, when to ask, and when to hold an agreed pause.

The prototype combines time and calendar context, tiered boundaries, explicit completion and optional work stops. The next test is whether that combination helps other developers more than their existing agent setup. A warm voice alone would not be enough.

The standard is real workflow utility. Planned trials will compare paperkinn with developers’ existing agent setups. We will check care-state accuracy, unwanted interruptions, effort needed to resume work and voluntary repeat use. These are evaluation goals, not measured results. Longer conversations are not the goal.
03Grounded in research

Deep focus can make a pause difficult.

Research on hyperfocus describes intense absorption and reduced awareness of competing demands. Monotropism is a theory of concentrated attention in autism. Neither describes every ADHD or autistic person.

Developer interviews add a practical view: starting, planning and returning to context can be difficult, even when the coding itself goes well. paperkinn uses these findings to guide its design, alongside experience with the working prototype.

  • A difficult transition. Help find a stopping point and leave a short record of the work.
  • Time slips from view. Use local time, calendar context and completed-action reports to inform care.
  • Too much to hold. Keep the current task and the next manageable action visible.

04Why Claude

The conversation matters as much as the code.

Claude is the starting point for paperkinn’s planned MCP integration. Anthropic’s character-training approach emphasizes thoughtfulness, honesty and respectful disagreement. That fits a companion that listens to the developer, considers the work in progress and can hold an agreed boundary without turning every detour into another task.

The model provides the conversation. Separate care rules track reminders, completed actions and whether an optional work stop remains active. MCP plugins are in development to bring that state into Claude-based agent workflows.

We will test whether that combination provides useful support without unwanted interruptions. Older studies of assistive interactions inform the choice, but do not prove paperkinn’s effectiveness or Claude’s superiority in coding workflows.
